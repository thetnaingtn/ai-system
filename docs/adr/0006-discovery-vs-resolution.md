# 6. Discovery is build-time; resolution is request-time; separate code paths

Date: 2026-08-30
Status: Accepted

Follow-up: [ADR-0031](0031-model-names-without-snapshots.md) replaces snapshot
reporting with requested and actual model name reporting. The discovery and
resolution separation remains accepted.

## Context

`ListModels` (what models exist) and chain resolution (which model serves this
request) both read the catalog. It is tempting to share a code path, and
tempting for the SDK to call `ListModels` at startup to validate names or cache
the catalog locally.

## Decision

- **Discovery** — `ListModels` / `GetModel`. Consumed by humans, IDEs, CI, and
  the CLI. Reads the store directly. May fail when the store is down.
- **Resolution** — inside `Generate`. Consumed only by the service's own code.
  Reads an in-process cache. Must survive a store outage.
- **Nothing on the request path calls the discovery API. The SDK never queries
  the catalog at runtime.**

## Rationale

The two consumers want opposite things:

| | Discovery | Resolution |
|---|---|---|
| Frequency | a few times a day | every request |
| Latency budget | seconds | sub-millisecond |
| Wants | all entries, rich metadata | one entry, minimal |
| Staleness | must be fresh | serve stale happily |
| If unavailable | a docs page breaks | the company is down |

No single caching policy, payload shape, or availability target is correct for
both.

If the SDK called `ListModels` at init: every client gains a startup dependency
on the catalog path; a deploy of 50 pods becomes a thundering herd; each pod
holds a catalog that drifts; and a listing query inherits the hot path's
availability requirements.

## Consequences

- **Runtime behavior is reported, not discovered.** Every response carries a
  `resolution` block: requested name, resolved catalog version, provider and
  **snapshot** that served it, attempt number, and what failed before it. A
  developer debugging never needs to find the catalog.
- **An invalid model name is a deploy-time error, not a runtime check.** Unknown →
  build fails; DEPRECATED → build warns with sunset date and replacement; past
  sunset → build fails. See "How the build-time check works" below for what this
  covers and what it does not.
- Deprecation requires no nagging — through three channels, not one. See
  "Deprecation reaches everyone" below.
- CI covers source; request telemetry covers reality, including services whose
  repos are dormant. Both are needed.
- Discovery should expose capabilities, status, and ownership — **not** the
  internal chain composition, so teams cannot couple to it.

## How the build-time check works

Two jobs with very different reliability. The original wording ("CI lints model
names") oversold the second.

**Policy files — exact.** `platform/policy.yaml` is structured and in a known
location, so `platformctl policy validate` checks every model name in it perfectly.
Same binary that runs at `policy apply` (ADR-0010).

**Application source — exact in Go, best-effort elsewhere.** In source a model name
is a string, and may be a constant, a config value, a database column, or built by
`fmt.Sprintf`. No linter catches the last one.

For Go the answer is codegen, not linting. `platformctl gen` emits typed constants,
and the SDK takes a `Model` type rather than a `string`:

```go
// Code generated by platformctl. DO NOT EDIT.
// Catalog version: 2026-09-13T08:14:22Z

const GPT4o Model = "gpt-4o"

// Deprecated: sunset 2026-11-01. Use ClaudeSonnet4.
const Claude35Sonnet Model = "claude-3-5-sonnet"
```

Unknown name is a **compile error**; `// Deprecated:` is flagged natively by
staticcheck and every Go IDE. We write no lint code and coverage is exact.

Generated files go stale, so CI runs a freshness check that diffs the catalog
against the constants the repo actually uses — not merely a timestamp comparison,
so the first message is already actionable:

```
$ platformctl gen --check

⚠ Model catalog is 47 days newer than internal/models/models.go

  Affecting models you use:
    claude-3-5-sonnet   DEPRECATED — sunset 2026-11-01 (49 days)
                        replacement: claude-sonnet-4
```

Python and TypeScript get generated modules too, but nothing enforces their use.
The fallback there is a scan of string literals against the catalog, and its output
must state its own limits ("scanned 34 literals") rather than imply completeness.

**Unreachable catalog fails open.** If `platformctl` cannot reach the catalog it
warns and exits zero. Violations fail closed; unavailability does not. A
model-service incident must not stop forty teams from merging — that blast radius
is worse than the original outage.

CI uses the workflow OIDC identity from ADR-0014 §11. Adoption is by a reusable CI
workflow teams include in one line; we cannot force anything into another team's
repo, which is why telemetry is also required.

## Deprecation reaches everyone

Flipping `status: DEPRECATED`, `sunset`, and `replacement` in the catalog is one
PR with no announcement. It reaches teams through three channels, each covering the
others' gaps:

| Channel | Reaches | Misses |
|---|---|---|
| `gen --check` in CI | repos with the lint | dormant repos, non-Go, non-adopters |
| `resolution.warnings[]` on every response | everyone, every request | nobody |
| Service refuses past sunset | everyone | — it is the deadline |

The response warning is language-agnostic and impossible not to receive. The SDK
logs it at WARN **once per process per model**, never per request — otherwise
nagging is replaced by log spam, which gets filtered and then ignored.

Escalation needs no human driving it, because the message is computed from
`sunset - today`: notice beyond 60 days, warning at 30–60, prominent countdown
under 30, build failure past sunset. Past sunset `Generate` returns
`FailedPrecondition` naming the replacement.

That last one is a production outage on a date we chose, for anyone who ignored
every prior signal. So the platform needs the matching view: **telemetry by tenant
for every deprecated model**, which ADR-0014 identity provides for free. "No
nagging" means we do not chase everyone; it does not mean we sunset blind. If three
teams are still calling it a week out, we contact those three.

CI covers source; telemetry covers reality. Before sunsetting, traffic is ground
truth and source scans are early warning.
