# AI platform data model

Updated: 2026-11-08
Status: Design draft; application tables have not been implemented.

This document describes the first model service's PostgreSQL tables, their
purpose, columns, relationships, and constraints. It is a working design for
discussion, not an executable migration or a declaration that every detail is
settled. Data, sessions, memory, and workflow tables follow later.

## Agreed direction

- Use PostgreSQL schemas to group tables by responsibility.
- Use one real model name across clients and provider requests, for example
  `gpt-4o`. No intent aliases, separate provider model IDs, or model snapshots.
- Keep endpoint configuration directly on the model row. No `endpoints` table.
- Store ordered fallback chains in versioned tenant policies as validated JSONB.
  Fallback is tenant-specific, not a column on the shared model row.
- Keep immutable prompt revisions and separate, conflict-checked releases.
- Keep temporary generation coordination and completed-response recovery in
  Redis. PostgreSQL is not a generation execution ledger.
- Store credential references, never credential values, in PostgreSQL.

The table inventory and exact columns below are proposed implementation details.
Budget accounting, approval mechanics, permissions storage, and several
concurrency rules still require decisions before implementation.

## Schemas and table inventory

| PostgreSQL schema | Table | Purpose |
|---|---|---|
| `model_catalog` | `models` | Shared model configuration, including endpoint fields |
| `model_catalog` | `model_change_requests` | Proposed changes and required approval decisions |
| `model_catalog` | `model_prices` | Effective-dated model pricing |
| `tenant_config` | `tenants` | Tenant ownership and operating tier |
| `tenant_config` | `policy_versions` | Immutable tenant policy documents |
| `tenant_config` | `policy_heads` | Active policy version for each tenant |
| `prompt_registry` | `prompts` | Scoped prompt identities and revision allocation |
| `prompt_registry` | `prompt_revisions` | Immutable system prompt text |
| `prompt_registry` | `prompt_releases` | Movable release tags such as `stable` |
| `usage_accounting` | `budget_periods` | Monthly tenant budget accounting |
| `usage_accounting` | `cost_reservations` | Admission reservations and reconciliation state |
| `usage_accounting` | `usage_records` | Observed provider-attempt usage and cost |
| `audit` | `events` | Safe metadata about privileged changes |

All schemas belong to the same model-service database. Use schema-qualified
table names in SQL. Keep one migration sequence under `model/migrations/` and
golang-migrate's version table in `public` with migration `search_path=public`.
The existing bootstrap migration creates an empty `model` schema; a subsequent
migration can replace that unused grouping with these schemas.

## Type and naming conventions

| Convention | Proposed PostgreSQL representation |
|---|---|
| Internal record IDs | `uuid`; generated by the application or `gen_random_uuid()` |
| Model names and tenant IDs | `text`; validated nonempty, case-sensitive identities |
| Revisions and configuration versions | Positive `bigint` |
| Timestamps | `timestamptz`, stored as instants and displayed in UTC |
| Monthly accounting period | `date`, the first calendar day of the UTC month |
| Monetary amounts | `numeric(24,12)`; never floating point |
| Currency | `text`; initially one configured currency, proposed `USD` |
| Constrained statuses | `text` with `CHECK` constraints rather than PostgreSQL enums |
| Structured policy/configuration | `jsonb`, with object-shape checks and service validation |

In the column tables, “No” means `NOT NULL`; “Yes” means nullable. Defaults and
status values are proposals unless established by an ADR. Unless stated otherwise,
foreign-key deletion should be restricted rather than cascading through history.
Do not rename model identities in place; register a new name and use the existing
deprecation/replacement lifecycle. Configuration versions are not model snapshots.

## 1. Model catalog

### `model_catalog.models`

One shared row per real model name. All clients refer to the same name, and the
adapter sends that name to the configured endpoint. A repeated endpoint URL or
secret reference across different model rows is allowed.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `name` | `text` | No | Primary key; real model name |
| `provider` | `text` | No | Adapter selector, such as `openai` or `anthropic` |
| `base_url` | `text` | No | Provider or self-hosted API base URL |
| `credential_secret_ref` | `text` | Yes | Secret-manager reference; null for an approved credentialless endpoint |
| `owner_tenant_id` | `text` | Yes | FK to `tenant_config.tenants`; null for platform-owned models |
| `config_origin` | `text` | No | `platform_config` or `runtime_registration` |
| `capabilities` | `jsonb` | No | Validated native feature support and context limits |
| `status` | `text` | No | Lifecycle: `active`, `deprecated`, or `sunset` |
| `sunset_at` | `timestamptz` | Yes | Scheduled retirement instant |
| `replacement_model` | `text` | Yes | FK to another model name; deprecation guidance |
| `accounting_mode` | `text` | No | `metered` or platform-approved `unmetered` |
| `approval_status` | `text` | No | `pending`, `approved`, or `rejected` |
| `config_version` | `bigint` | No | Incrementing configuration revision for concurrency and reporting |
| `created_at` | `timestamptz` | No | Creation time |
| `updated_at` | `timestamptz` | No | Last configuration change time |

Proposed capability document:

```json
{
  "tools": true,
  "structured_output": false,
  "streaming": true,
  "vision": false,
  "max_context_tokens": 128000
}
```

Require the known capability fields and validate their types. These describe
native support; no structured-output emulation is promised in v1. Adapter support
must also be checked before routing.

Constraints and behavior:

- `name` is globally unique; `config_version > 0`; a replacement cannot be self.
- Lifecycle status alone does not authorize execution. Serving also requires
  approval, tenant authorization, capabilities, and applicable accounting checks.
- A metered model without applicable pricing is blocked. Unmetered status requires
  platform approval; it does not remove rate or concurrency protection.
- The initial approval rules for priced registrations remain open. The draft
  approval column does not impose new approval gates beyond ADR-0029.
- A pending replacement leaves this row's currently approved configuration intact.
- Validate endpoint destinations and prohibit credentials embedded in URLs.
  Secret references and internal endpoint details are not public discovery fields.
- Updates compare the expected `config_version`; name-conflicting registration
  is not an update. Exact registration equality rules still need specification.

### `model_catalog.model_change_requests`

Stages changes requiring review, particularly endpoint replacements and unmetered
requests. It preserves the active configuration while review is pending.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `model_name` | `text` | No | FK to the model being registered or changed |
| `change_type` | `text` | No | Proposed values: `registration`, `endpoint_change`, `unmetered_request` |
| `expected_config_version` | `bigint` | No | Model revision on which the proposal was based |
| `proposed_config` | `jsonb` | No | Validated proposed fields; secret references only |
| `status` | `text` | No | `pending`, `approved`, or `rejected` |
| `requested_by` | `text` | No | Authenticated principal requesting the change |
| `reviewed_by` | `text` | Yes | Authorized reviewing principal |
| `decision_reason` | `text` | Yes | Sanitized decision explanation |
| `created_at` | `timestamptz` | No | Request time |
| `decided_at` | `timestamptz` | Yes | Review completion time |

This draft reserves a new name with a pending model row before recording its
registration proposal. Such a row cannot serve until all required gates pass.
An initial registration's reserved row may use version 1; approval then increments
the version. Whether to allow multiple pending changes per model remains open.

Approval must compare the expected configuration revision, update the model,
record the decision, and append an audit event in one transaction. Rejection
preserves the active configuration. Credential rotation does not require endpoint
reapproval; secret-manager writes require separate cleanup/reconciliation because
they cannot participate in the PostgreSQL transaction.

### `model_catalog.model_prices`

Retains pricing used to estimate and reconcile provider spend. Pricing is
platform-managed. This draft covers token-based charging; other billing dimensions
need explicit extension rather than being treated as zero.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `model_name` | `text` | No | FK to `model_catalog.models` |
| `currency` | `text` | No | Accounting currency |
| `input_per_million_tokens` | `numeric(24,12)` | No | Input-token price |
| `output_per_million_tokens` | `numeric(24,12)` | No | Output-token price |
| `cached_input_per_million_tokens` | `numeric(24,12)` | Yes | Optional separately priced cached input |
| `effective_from` | `timestamptz` | No | Inclusive validity start |
| `effective_until` | `timestamptz` | Yes | Exclusive validity end; null means open-ended |
| `created_by` | `text` | No | Authorized publishing principal |
| `created_at` | `timestamptz` | No | Publication time |

Require nonnegative prices, increasing validity bounds, and non-overlapping price
intervals per model/currency. Historical rate values are not overwritten; preserve
price references from accounting records. Missing pricing is not a zero price.
The meaning of a missing cached-input rate must be settled before that feature is
used for reservations or reconciliation.

## 2. Tenant configuration

### `tenant_config.tenants`

Stores ownership and operating-tier metadata. Tenant identity is proven at the
transport boundary, not accepted from a generation request body.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `text` | No | Primary key; authenticated tenant identifier |
| `owner` | `text` | Yes | Responsible team/person contact |
| `cost_center` | `text` | Yes | Accounting attribution |
| `tier` | `text` | No | `experimental` or `production` |
| `review_by` | `date` | Yes | Review date for experimental access |
| `created_at` | `timestamptz` | No | Metadata creation time |
| `updated_at` | `timestamptz` | No | Last metadata update |

Production requires owner and cost center. Unknown but authenticated tenants
receive experimental defaults; registration is not an onboarding gate. When a
durable write needs a tenant FK, establish its default row atomically. Cold-start
and PostgreSQL-outage behavior must still respect ADR-0027 and quota availability.

### `tenant_config.policy_versions`

Stores complete immutable tenant policy documents, including fallback chains.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `tenant_id` | `text` | No | FK to `tenant_config.tenants`; part of primary key |
| `version` | `bigint` | No | Positive tenant-local revision; part of primary key |
| `document` | `jsonb` | No | Validated policy object |
| `created_by` | `text` | No | Authenticated publishing principal |
| `source_revision` | `text` | Yes | Publishing repository commit or equivalent provenance |
| `created_at` | `timestamptz` | No | Publication time |

Primary key: `(tenant_id, version)`. Example policy fragment:

```json
{
  "allowed_providers": ["openai", "anthropic"],
  "fallbacks": {
    "gpt-4o": ["claude-sonnet"]
  },
  "retry": {
    "max_attempts_per_target": 2
  }
}
```

This fragment is illustrative, not the complete policy contract. Each mapping
key is the requested primary model; the array is its ordered fallback list.
Missing entries mean no fallback. These are direct ordered lists, not recursive
lookups of another model's policy entry.

JSONB model references cannot use ordinary model-name foreign keys. The service
must validate names, lifecycle, capability coherence, provider permissions, retry
caps, and publishing authorization on apply. Runtime checks still enforce current
restrictions. Numeric quota values, document schema/defaults, and validation
behavior during concurrent catalog changes remain to be finalized.

### `tenant_config.policy_heads`

Selects the active immutable policy for each tenant. Rollback changes this pointer
to an older version rather than rewriting a historical policy.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `tenant_id` | `text` | No | Primary key; FK to `tenant_config.tenants` |
| `active_version` | `bigint` | No | Selected policy revision |
| `updated_by` | `text` | No | Authorized principal performing activation |
| `updated_at` | `timestamptz` | No | Activation time |

Composite FK `(tenant_id, active_version)` references `policy_versions`.
Publication allocates a unique revision and activates it transactionally. The
exact version-allocation and compare-and-set protocol remains open. No head row
means use platform experimental/default policy behavior, including no fallback.

## 3. Prompt registry

### `prompt_registry.prompts`

Identifies a prompt by explicit scope and name and serializes revision allocation.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `scope` | `text` | No | `tenant` or `organization` |
| `tenant_id` | `text` | Yes | FK to tenant; required only for tenant scope |
| `name` | `text` | No | Name within its scope |
| `next_revision` | `bigint` | No | Next revision number; initially 1 |
| `created_by` | `text` | No | Authenticated creating principal |
| `created_at` | `timestamptz` | No | Creation time |

Require tenant scope to have a tenant ID and organization scope to have none.
Use `UNIQUE NULLS NOT DISTINCT (scope, tenant_id, name)` so organization prompt
names remain unique despite their null tenant ID. Require `next_revision > 0`.
Scope is explicit during lookup; missing tenant prompts never fall through to an
organization prompt with the same name.

### `prompt_registry.prompt_revisions`

Stores immutable plain system prompt text. It is functional storage and must not
be copied into diagnostic logs, traces, or audit event details.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `prompt_id` | `uuid` | No | FK to `prompts`; part of primary key |
| `revision` | `bigint` | No | Positive allocated revision; part of primary key |
| `content` | `text` | No | Exact system prompt text |
| `content_hash` | `bytea` | No | SHA-256 of the exact registered text |
| `created_by` | `text` | No | Authorized registering principal |
| `created_at` | `timestamptz` | No | Registration time |

Primary key: `(prompt_id, revision)`. Unique constraint:
`(prompt_id, content_hash)`. Require a 32-byte hash and positive revision.

Lock the parent prompt row when deduplicating and allocating revisions. Compare
stored text before reusing a hash match; a collision is an explicit error, not
deduplication. Preserve whitespace and newlines. Identical content returns the
existing revision without advancing a release tag. New content allocates a
revision and advances `next_revision` in the same transaction.

### `prompt_registry.prompt_releases`

Maps a prompt's release tag to an immutable revision. Default selection uses
`stable`, but registration never creates that tag automatically.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `prompt_id` | `uuid` | No | Part of primary key |
| `tag` | `text` | No | Part of primary key; for example `stable` |
| `revision` | `bigint` | No | Target revision |
| `updated_by` | `text` | No | Authorized releasing principal |
| `updated_at` | `timestamptz` | No | Last tag movement |

Primary key: `(prompt_id, tag)`. Composite FK `(prompt_id, revision)` references
`prompt_revisions`. Tag creation requires an expected-absent condition; updates
require the expected current revision. A mismatch returns a conflict. Rollback
uses the same protocol to move the tag to an earlier revision.

Keep all revisions in v1; physical deletion is deferred. Durable reference
tracking and retention beyond this baseline remain open. Permissions for
`prompt.register` and `prompt.release` are separate and must be checked using
authenticated workload identity. Their storage/configuration is not decided here.

## 4. Usage accounting — proposed, not finalized

ADR-0028 requires reservations and reconciliation, but does not settle their
storage or outage behavior. The following three tables are a candidate durable
accounting design. Before migration, decide whether PostgreSQL or Redis owns
atomic admission, how durable records are updated, and what happens when that
enforcement state is unavailable. This proposal does not require a PostgreSQL
write on every generation or override cached inference during PostgreSQL outages.

### `usage_accounting.budget_periods`

Tracks a tenant's budget and accounting totals for a UTC calendar month.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `tenant_id` | `text` | No | FK to tenant; part of primary key |
| `period_start` | `date` | No | First UTC day of month; part of primary key |
| `currency` | `text` | No | Accounting currency |
| `limit_amount` | `numeric(24,12)` | No | Authorized monthly spend cap |
| `reserved_amount` | `numeric(24,12)` | No | Cost held for admitted or uncertain work |
| `spent_amount` | `numeric(24,12)` | No | Reconciled observed cost |
| `updated_at` | `timestamptz` | No | Last accounting update |

Primary key: `(tenant_id, period_start)`. Require first-day dates and nonnegative
amounts. A spent total may exceed the cap due to already admitted work or later
reconciliation; do not impose a constraint that prevents recording real cost.
Use atomic reservation updates in whichever store owns admission. No implicit
unlimited budget is represented by a missing row.

### `usage_accounting.cost_reservations`

Tracks estimated exposure and settlement. Attempt-level reservations are proposed
because fallback and recovery can incur charges at more than one provider.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `tenant_id` | `text` | No | Charged tenant |
| `period_start` | `date` | No | Assigned budget month |
| `operation_id` | `uuid` | No | Correlation identity for a logical generation |
| `attempt_id` | `uuid` | No | Unique provider-attempt identity |
| `model_name` | `text` | No | FK to the attempted model |
| `price_id` | `uuid` | No | FK to the price used for estimation |
| `reserved_amount` | `numeric(24,12)` | No | Estimated maximum charge |
| `settled_amount` | `numeric(24,12)` | Yes | Observed final charge, if known |
| `status` | `text` | No | Proposed: `reserved`, `settled`, `released`, `uncertain` |
| `created_at` | `timestamptz` | No | Reservation time |
| `reconcile_after` | `timestamptz` | No | Time to investigate unresolved work |
| `settled_at` | `timestamptz` | Yes | Reconciliation completion time |

Composite FK `(tenant_id, period_start)` references `budget_periods`; `attempt_id`
is unique. Monetary amounts are nonnegative. Unmetered models need no provider
spend reservation but still require usage tracking and capacity limits.

Do not release a reservation merely because a timer or owner lease expired: the
provider may still be charging. Missing usage remains uncertain. Month attribution,
reservation sizing across retries, and recovery reconciliation remain undecided.
These are accounting records, not a prerequisite execution ledger for generation
deduplication or a promise of exactly-once execution.

### `usage_accounting.usage_records`

Records observed provider-attempt usage, including failed attempts and recovery
attempts when their usage can be observed. It contains no generation payloads.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `tenant_id` | `text` | No | FK to charged tenant |
| `operation_id` | `uuid` | No | Logical generation correlation |
| `attempt_id` | `uuid` | No | Unique attempt/reconciliation identity |
| `reservation_id` | `uuid` | Yes | FK to corresponding cost reservation |
| `model_name` | `text` | No | FK to actual attempted model |
| `config_version` | `bigint` | No | Model configuration used by the attempt |
| `price_id` | `uuid` | Yes | FK to applicable historical price |
| `period_start` | `date` | No | Accounting month attributed to the attempt |
| `input_tokens` | `bigint` | Yes | Observed input usage; null means unknown |
| `output_tokens` | `bigint` | Yes | Observed output usage; null means unknown |
| `cached_input_tokens` | `bigint` | Yes | Observed cached-input subset |
| `cost_amount` | `numeric(24,12)` | Yes | Known cost; null means unknown |
| `currency` | `text` | No | Accounting currency |
| `accounting_status` | `text` | No | Proposed: `observed`, `uncertain`, `unmetered` |
| `outcome` | `text` | No | Sanitized execution outcome category |
| `started_at` | `timestamptz` | No | Attempt start |
| `completed_at` | `timestamptz` | Yes | Observed attempt completion |
| `recorded_at` | `timestamptz` | No | Accounting record time |

Require unique `attempt_id` and nonnegative known counts and costs. Ensure cached
input does not exceed known total input. Reconciliation must update accounting
idempotently; it must not increment spend again for a duplicate report. Unknown
cost is never recorded as zero. How to capture later observations while preserving
accounting history remains open. Validate that linked tenant, model, price,
reservation, period, and currency agree; independent FKs alone are insufficient.

## 5. Audit

### `audit.events`

Append-only records of privileged operations: model changes/approvals, credential
rotation metadata, policy activation/rollback, and prompt registration/release.

| Column | Type | Nullable | Purpose |
|---|---|---|---|
| `id` | `uuid` | No | Primary key |
| `actor_principal` | `text` | No | Proven identity performing the action |
| `tenant_id` | `text` | Yes | Tenant context, if applicable |
| `action` | `text` | No | Stable action identifier |
| `resource_type` | `text` | No | Model, policy, prompt, or other audited resource |
| `resource_id` | `text` | No | Resource identifier |
| `outcome` | `text` | No | Sanitized result category |
| `details` | `jsonb` | No | Allowlisted IDs, versions, and changed field names |
| `occurred_at` | `timestamptz` | No | Event time |

Do not store arbitrary request objects or full before/after documents in audit
details. Exclude credentials, prompt text, messages, tools, and responses. Resource
references are descriptive, not polymorphic foreign keys. Successful durable
changes should append their event in the same transaction. Policy for failed
operations and audit retention remains open.

## Relationships and indexes

- Models reference optional owning tenants and replacement model names. Prices
  and change requests reference model names.
- Policies are tenant-local versions; a head points to a version of the same tenant.
- Prompt identity owns revisions; each release points to a revision of that prompt.
- Budget periods own reservations; usage references prices and optional reservations.
  Accounting operation IDs correlate with Redis operations without a PostgreSQL
  operation-table FK.
- Primary keys and unique constraints provide their indexes. Add indexes on
  frequently joined foreign keys and access paths, initially proposed:
  `models(owner_tenant_id)`, `model_change_requests(model_name, status)`,
  `model_prices(model_name, effective_from)`,
  `cost_reservations(status, reconcile_after)`,
  `usage_records(tenant_id, period_start)`, `usage_records(operation_id)`, and
  `audit.events(resource_type, resource_id, occurred_at)`.
- Do not add a JSONB GIN index by default. Policy lookup loads one active document
  by tenant; it does not require indexing every policy field.

## Remaining design work

- Finalize endpoint validation, registration equality, approval transitions,
  conflicting pending changes, and platform-config/runtime ownership rules.
- Finalize policy document fields, revision allocation, activation concurrency,
  workload permission configuration, and incident-disable storage with 24-hour expiry.
- Select the secret-manager backend and credential refresh/cleanup mechanics.
- Settle accounting authority, storage, limits, currency, billing dimensions,
  month boundaries, and outage/uncertainty behavior before implementing those tables.
- Define cache refresh, revocation visibility, configuration version reporting,
  and whether catalog-wide publication history needs additional storage.
- Define prompt reference tracking, retention, and audit access/retention rules.
